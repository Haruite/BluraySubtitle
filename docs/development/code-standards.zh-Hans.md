# 代码修改规范

[English](code-standards.md) | 简体中文

## 1. 权威来源与适用范围

本规范适用于仓库的所有修改，必须遵守。仓库文档与代码发生冲突时，按以下顺序确定依据：

1. 本规范；
2. `README.md` 和 `README.zh-Hans.md` 描述的产品行为；
3. 实现细节。

针对特定文件或工作流的明确要求优先于对应的通用规则；产品例外集中列在第 10 节。

本规范的中英文版本必须保持同步；作者确认的规则须在依赖它的代码修改之前或同一次修改中记录。记录已确认的产品行为或使用注意事项时，同步更新中英文 README。重构或重大改动还须更新[英文](../refactoring/refactoring-history.md)和[简体中文](../refactoring/refactoring-history.zh-Hans.md)重构历史；一般修改无需历史记录。重构历史仅记录实际改动和必要的验证结果，不记录未改动事项及未落实为改动的讨论，也不作为当前规范或行为约束的依据。

## 2. 简单与一致

- 使用最简单的正确实现；在本次修改范围内删除重复、冲突、不可达或不必要的逻辑。
- 只增加本次已确认需求所需的校验或抽象。优先使用结构或字面量检查；只有格式本身属于需求时才使用严格的正则表达式匹配。
- 在负责接收该事实的边界执行校验；只有输入或相关外部状态可能变化时才重复检查。
- 共用行为只保留一份实现；不能仅因代码相似就耦合无关工作流。
- 优先用一个函数完成一项内聚的操作。避免只转发调用的辅助函数或无意义拆分，也不要为减少函数数量而合并无关职责。
- 导入、类型标注、异常处理和格式与所在模块保持一致。
- 仅在仓库内部调用方或已确认需求需要时，保留兼容包装层或 facade API。
- 只在明确的 GUI/Worker 边界或尽力清理边界捕获宽泛异常；必须明确处理失败，不能隐藏无效配置或执行失败。

## 3. 源码语言、注释与命名

- Python 字符串字面量以及所有代码注释和 docstring 均使用英文；翻译目录 `I18N_ZH_TO_EN` 的中文键是明确例外。
- 注释应解释关键领域规则、不直观的计算、所有权边界和有意保留的例外；不重复显而易见的代码含义。
- 变量、函数、类和字段的名称应表达对应的领域值或操作。作用域很小的索引可使用惯用短名称。

## 4. GUI 是执行契约

- 主窗口仅固定顶部语言／主题／字体／设置栏与底部执行按钮，其余内容纵向滚动；表格须保留足够的可读高度。
- 除第 10 节列出的例外外，执行必须采用任务启动时捕获的 GUI 可见值：已选行、路径、名称、语言、模式、命令、章节范围、编码器及其他选项。
- 执行顺序采用已捕获的可见表格顺序，除非 GUI 明确说明其他排序规则。
- 不得静默跳过选择项，也不得用过期状态、全局值、默认值、重新生成值或推断值替换显式值。已选行或选项无法执行时必须报错；只有用户未提供值时才可推断。
- 长时间任务在 GUI 线程之外执行，并保持进度、取消、成功和错误处理一致。

## 5. 预检查与失败处理

- 启动 Worker 或写入输出前，检查 Request 的路径、选择项、所需工具、区间、映射、命令结构及完整输出计划中的确定性错误与冲突。不得重复执行昂贵的媒体探测，也不得在没有已确认规则时增加限制。
- 执行时才发现的媒体相关失败必须指出受影响的源文件或行，并明确报错。
- 已存在的计划输出属于冲突，只有已确认的可恢复工作流将其明确记录为已完成输出时才可跳过，并须逐项报告。不得覆盖、改名或复用冲突输出，也不得通过改变计划路径来绕过冲突。
- 检查每条外部命令的退出状态。优先使用参数列表和 `shell=False`；只有需要 shell 语法时才使用 shell。警告退出码的含义须已在该工具中得到记录或验证，才可接受。
- 清理只能删除当前任务创建的临时或不完整产物，不能删除任务开始前已有的文件。Encode 行失败时，非空产物须以唯一且不作为最终输出的名称保留并列入错误报告，只有该行最终输出成功后才能删除。
- Encode 批处理中，请求级安全失败、用户取消和不安全状态须停止整批任务；仅影响单行的失败须记录并继续后续行。Worker 清理完成后统一显示一次摘要，批处理期间不显示模态错误。

## 6. 分层职责

- GUI/配置层：启动时一次性读取当前控件，仅规范化表示形式而不改变其含义，执行确定性预检查并创建完整 Request。可行时使用一个显式 Request 对象。
- Worker 层：拥有已捕获的 Request、进度回调、取消状态及最终成功/错误信号；启动后不得读取实时 GUI 控件。
- Service 层：根据普通 Python 数据执行工作流和领域逻辑，不读取或重新解释 Qt 表格与控件，也不查询隐藏全局状态。
- 领域/工具层：执行可复用的媒体计算和显式外部工具操作。
- 避免可变的模块级工作流配置；共享领域计算和写入原语时，不共享过期的工作流状态。
- 同一配置不得既通过 Service 属性提供，又作为方法参数传递。
- `src/runtime/gui_runtime_split` 和 `src/runtime/services_split` 中的 mixin 方法，须分别在 `gui_base.py` 和 `service_base.py` 中有签名一致的声明。

## 7. i18n 与用户文档

- 由程序定义的用户可见文本，包括 GUI 标签、对话框、进度和终端信息，必须支持英文和简体中文。在同一次修改中更新 `src/core/i18n.py:I18N_ZH_TO_EN`：中文文本为键，对应的英文源字符串为值。
- 在展示边界通过 `self.t(...)` 或 `translate_text(...)` 翻译。动态文本先翻译稳定模板，再填入具体值。
- README 只保留当前功能、使用注意事项和其他对用户有效的信息。实现细节仅放在专门的“实现说明”或“实现细节”段落与章节中；历史行为对比、已删除行为和重构原因写入重构历史；未来清理计划写入开发文档。

## 8. 文件格式

- 源码和文档使用 UTF-8。新增或修改的文本文件使用 CRLF；shell 脚本和 Dockerfile（`Dockerfile`、`*.dockerfile`）使用 LF，以保证 shebang 和 shell heredoc 正常工作。
- Markdown 段落尽量写在一行；正文需要拆行时，只在完整句子的边界换行。保留列表、表格、代码块、图示等结构所需的换行，每个列表项独占一行。
- 不引入行尾空格或错误编码。

## 9. 工具版本与 Dockerfile 维护

- 支持的操作系统与架构以 `setup_windows_environment.ps1` 和 `setup_linux_environment.sh` 接受的范围为准：当前为 x64 Windows 10 及以上、带桌面体验的 Windows Server 2019 及以上、Ubuntu 22.04 及以上和 Debian 12 及以上。修改须考虑整个支持范围，不能只验证开发机，也不为范围外系统增加兼容分支。Linux 功能还须评估仓库的 Docker 运行环境；无法在 Docker 中运行的功能不得宣称支持 Docker。
- 依赖与随附工具使用官方上游发布的最新版本；只有已确认的兼容性问题或其他技术约束才允许固定版本或提交。
- 安装脚本和 Dockerfile 须安装各自运行环境使用的全部可执行程序、库和插件；源码构建须显式启用程序使用的全部可选功能。
- `Dockerfile` 是 `setup_linux_environment.sh` 面向 Ubuntu 26.04 的适配版。不得在 Dockerfile 中增加其他操作系统的兼容处理、说明性输出或注释。
- Linux setup 须将受管理的可执行文件和 VapourSynth 插件安装到 `src/core/settings.py` 定义的 Linux 路径。Docker 须在各工具构建段内直接安装到该文件中对应的 Docker 路径，不得增加末尾统一搬运层。
- 已有软件必须在 Dockerfile 对应构建段内修改，即使后续层缓存因此失效。不得把无关改动放到文件前部；新增软件在依赖关系允许时尽量放到末尾，以保留前面构建层的缓存。

## 10. 已确认的产品约束

本节只记录已确认的例外和容易产生歧义的产品语义。实现细节写入相邻代码注释或重构历史。

- **ISO 合并字幕：** ISO 输入仅用于读取 BDMV 播放列表并合并字幕，不支持预览、Remux 或 Encode。读取完播放列表即释放镜像访问，不在任务期间持续挂载镜像。
- **Dolby Vision 增强层：** Dolby Vision Remux 或 x265 压制前识别 MEL／FEL，识别失败按 FEL 处理。Remux 仅在不丢弃图像残差的情况下转换为 P8.1，否则保留 P7。x265 可仅压制基础层而不利用 FEL 残差，并在现有完成弹窗中提示此限制。SVT-AV1 统一提示不会保留 Dolby Vision，不区分 MEL／FEL。这两类限制均不使 Encode 失败，也不要求事先确认。
- **主播放列表 Remux 选轨：** 视频、音频和字幕选择以“编辑轨道”为准。可编辑混流命令使用 `{video_opts}`、`{audio_opts}` 和 `{sub_opts}` 占位符；手工填写的选轨参数会被忽略，执行时根据已捕获的轨道选择替换。
- **自动 getnative：** 实际源高度超过 1080 像素时，即使已勾选选项，Encode 也会报告并跳过自动 getnative。更高分辨率的分析须手动运行 `src/scripts/getnative_file.py` 并配置 VPy。
- **Encode 恢复执行：** Remux 来源 Encode 跳过已完成的正片、SP、外挂字幕和附带文件输出且不覆盖，再继续其余任务。正片/SP 文件须非空；目录来源行须有对应的预期目录输出。空正片/SP 文件或类型错误的路径必须报错。已有外挂字幕和附带文件视为已完成。当前请求内部的重复路径仍然报错。
- **原盘 DIY：** 保持功能可见并保留代码；不得把未完成的执行表现为已完成。
- **自动移除音轨：** 最终 Remux 和 Encode 输出可移除已选的静音音轨和解码后完全相同的重复音轨，并逐项报告。
- **MPLS 逻辑轨道：** 加载时仅根据完整播放列表的 STN 构建选轨列表。同一 MPLS 内，STN 类别和 Stream Number 序号标识跨 PlayItem 的一条逻辑轨道；PID 变化或仅在部分片段存在不构成不同逻辑轨道。“编辑轨道”每条逻辑轨道显示一行，列出全部不同 PID、简明状态，并在提示中展开逐 PlayItem 时间线。语言变化仅作提示，默认语言仍取第一个非 `und` 的明确语言。
- **轨道片段缺失：** STN 已声明的片段在对应 M2TS 的 PAT/PMT 中缺失时，默认使输出失败。默认关闭的“允许非视频轨道部分缺失”策略，仅在 PAT/PMT 确认缺失、tsMuxer 无法提供且同一逻辑轨道在输出其他位置存在时，才可将该音频或字幕片段改为时间线空档。已选轨道在整个输出中缺失、任何视频片段缺失或任何传输格式冲突都必须明确失败。
- **传输格式兼容性：** MPLS 与 M2TS PAT/PMT 检查仅使用这些结构公开的参数。作者确认策略前，不得为 Matroska 追加不兼容增加推测性的全载荷解析或格式归一化，例如只能从载荷发现的 PCM 位深／声道布局或 codec-private 变化。MKVToolNix 遇到此类变化时必须明确失败；不得合成替代数据包、静默丢弃其他轨道或将不完整文件作为最终输出。
- **跨 MPLS 轨道身份：** 按 `(M2TS 绝对路径, PID)` 对应关系的集合比较轨道。持久化选轨标识须包含来源 MPLS 及其 STN 类别／槽位；不得仅按 PID 或槽位对不同来源去重。
- **音频转换：** FLAC、AAC 和 Opus 转换须保留逻辑音轨开头和中间的时间线空档，不得合成静音。实际连续 PCM 区间作为一个事务处理和验证；任一区间失败都保留完整原音轨。时长损失回退不计编排空档，取单个区间正向缩短量的最大值，不累加各区间损失。
- **音轨间隙伴随文件：** 间隙检测后，Remux 须为每个输出保存一个伴随文件，记录存在空档的轨道；全部音轨连续时保存有效的空记录。Remux 来源 Encode 优先读取有效且与来源匹配的伴随文件，包括空记录；否则在单次来源音频解码中检测真实数据包时间线。没有元数据不能作为轨道连续的依据。
- **码率：** FDK-AAC 和 Opus 的码率 `0` 表示“自动”；正数表示明确的 kbps 目标。
- **剧集模式 SP 匹配：** 比较完整 M2TS detail，即片段名称、顺序和时间范围。先判断非主 MPLS 是否与唯一一个完整的已选主 MPLS 匹配，匹配时将轨道选择加入共享主重混流。否则，只有匹配唯一一集的 SP 才在分集后追加。跨多集的部分匹配保持普通 SP；电影模式不使用以上任一附加路径。
- **SP 默认选轨：** 整条主 MPLS 匹配时，聚合物理 M2TS/PID 关系不重叠的轨道，按代表 PID 排序后统一执行一次共用默认选轨算法。单集匹配时，分别对主 MPLS 与 SP MPLS 执行该算法，实际附加时再次按物理关系去重。

## 11. 测试与修改报告

- 缺陷修复不得新增或修改测试文件，除非修复同时属于大型且重要。大型功能或重构确需修改测试时，只覆盖关键且容易出错的行为。
- 保持测试精简：只保留关键计算、轨道与时间线身份、输出安全及影响结果的失败处理测试。不对功能细节面面俱到，不编写仅检查源码字符串、GUI 布局、默认值或内部调用转发的测试。断言行为与结果，合并重复场景，删除不再使用的测试辅助代码。
- mock 的工具结果只能验证程序决策，不能证明媒体正确性。音画同步、码流完整性及编码器／混流工具的实际行为须用有代表性的真实素材检查。
- 一般修改只运行与本次行为直接相关的测试。仅在大型重构、涉及范围较广的功能改动，或针对性测试结果表明存在可信的更广泛回归风险时，运行完整测试。
- 每次修改都执行 `git diff --check` 并验证文本文件的编码和换行符。其他检查按范围选择：Python 编译／导入冒烟测试、相关单元测试、源码语言／i18n 修改对应的 `tools/check_i18n.py`，以及 mixin／基类修改对应的 `tools/check_split_contracts.py`。
- 完整蓝光和 MKV 素材用于手动回归，不作为 CI 测试素材。仍需真实素材检查时，须说明检查内容、会写入什么，以及是否需要可丢弃副本。
- 每批修改结束时，报告修改文件与区域、删除的冗余或冲突、每项业务逻辑的修改前后行为、检查及结果、待完成的真实素材检查，以及适用的 README、i18n、规范和历史更新。
