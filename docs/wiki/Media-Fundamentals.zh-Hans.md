# 媒体基础概念

[English](Media-Fundamentals.md) | 简体中文

本页介绍 BluraySubtitle 文档中使用的基础概念。最重要的区别是：

> 容器负责组织轨道；编解码格式负责规定轨道中的样本如何表示。

因此，`.mkv` 与 H.264 或 HEVC 并不是同一层次上的“视频格式”。Matroska 是容器；H.264、HEVC、FLAC、TrueHD、PGS 等格式可以是容器内各轨道的内容。

## 媒体的分层模型

可以将媒体理解为以下几个层次：

| 层次 | 回答的问题 | 示例 |
| --- | --- | --- |
| 原盘／应用结构 | 播放器应播放什么，并以什么顺序播放？ | BDMV、MPLS、CLPI |
| 传输流或容器 | 各条流如何存储和同步？ | M2TS、MKV、MP4 |
| 轨道 | 这是哪一条独立媒体流？ | 主视频、评论音轨、PGS 字幕 |
| 编解码或基本流格式 | 轨道中的样本如何表示？ | H.264、HEVC、LPCM、FLAC、AC-3、PGS |
| 解码后样本 | 解码器最终产生什么？ | 视频帧、PCM 音频样本、字幕位图 |

混淆这些层次很容易导致错误表达。“把 MKV 转成 HEVC”将容器和编解码格式混为一谈。更准确的表达通常是：“解码 MKV 中的视频轨，将其编码为 HEVC，再把结果混流到 MKV 容器中。”

## 容器与轨道

**容器（container）**用于存储一条或多条同步媒体轨道及其元数据。常见内容包括：

- 一条或多条视频轨；
- 一条或多条音轨；
- 字幕轨；
- 章节；
- 字体、封面等附件；
- 标签，以及轨道语言、名称、默认和强制显示标记。

**轨道（track）**是容器中可独立寻址的一条流。同一 MKV 内的两条日语音轨即使使用相同编解码格式，仍然是两条独立轨道。轨道顺序、语言、名称和默认／强制标记是这些流的元数据，不属于解码后的声音或画面。

轨道编号由具体工具定义。传输流 PID、MKVToolNix 轨道 ID、Matroska `TrackNumber` 和 GUI 行号是不同的标识符。BluraySubtitle 必须显式映射这些标识，不能假设同一个整数在每一层都表示同一条轨道。

## MKV 与 Matroska

**Matroska** 是一种基于 EBML 的可扩展多媒体容器。`.mkv` 通常用于包含视频的 Matroska 文件。相关扩展名约定包括：

- `.mka`：以音频为主的 Matroska 文件；
- `.mks`：以字幕为主的 Matroska 文件；
- `.mk3d`：立体视频。

这些扩展名描述的是容器用途，而不是不同的编解码格式。Matroska 能够容纳多种视频、音频和字幕格式，并能表示章节、附件、标签、轨道语言、轨道名称以及时间戳空隙。

从高层看，Matroska 文件包含 EBML 头和一个 `Segment`。重要的 `Segment` 子元素包括：

- `Info`：时间刻度、时长、标题和写入程序；
- `Tracks`：各轨道的编解码信息和元数据；
- `Cluster`：带时间戳的媒体块；
- `Cues`：跳转索引；
- `Chapters`；
- `Attachments`；
- `Tags`。

Matroska 时间戳属于容器时间线。提取原始基本流可能丢失只存在于容器层的信息。例如，MKV 可以通过时间戳表示一段空隙，而提取出的裸 TrueHD 流只是连续排列的帧字节，本身无法保留这段 Matroska 时间空隙。

### 为什么项目使用 MKV，而不是更常见的 MP4

MP4 是很优秀的分发容器，在浏览器、手机、电视和剪辑软件中拥有广泛支持。它并不比 MKV“画质差”，因为容器选择不会改变视频解码后的画面。BluraySubtitle 使用 MKV，是因为项目主要任务是保留并重新组织原盘内容，而不是只面向某个受限分发平台。

在本项目的工作流中，Matroska 可以切实容纳多条视频、音频和字幕轨及其独立语言、名称和默认／强制标记；能保存原盘和归档 Remux 常见的无损音频、PGS 与 ASS；能保存章节、标签、时间戳行为和 ASS 所需字体附件；还能生成 `.mka` 纯音频与 `.mks` 纯字幕输出。MKVToolNix 同时提供抽取、追加、裁切、章节写入、附件处理和元数据验证。

MP4 所基于的 ISO Base Media File Format 本身可以扩展，特定 MP4 变体能保存的内容也可能多于普通播放器接受的范围。但实际 MP4 互操作子集更窄：ASS 和 PGS 不是常规 MP4 字幕选择，字体也不像 Matroska 那样作为字幕附件处理，部分蓝光音频还需要转换或依赖播放器特有映射。强行选择 MP4 可能导致轨道转换、呈现元数据丢失或必须外挂文件。

目标设备或服务明确要求 MP4，且已经确认其支持的编解码组合时，应选择 MP4；需要优先保留所选源轨及元数据时，本项目选择 MKV。只有每条所选流都存在兼容 MP4 映射时，MKV → MP4 才只是 Remux，否则还必须转换相应轨道。

## 基本流

**基本流（elementary stream）**只包含一条编码流，不带外围的多轨容器。常见示例包括：

- `.h264` 或 `.avc`：AVC 基本流；
- `.hevc` 或 `.h265`：HEVC 基本流；
- `.ac3`、`.dts`、`.thd`、`.flac`：音频流；
- `.sup`：蓝光 Presentation Graphics 字幕。

文件扩展名只是约定，并不能证明文件内容。可靠的软件应检查位流或容器元数据，而不能只相信后缀名。

## Demux／抽流

**Demultiplexing** 通常简称 **demux**，中文常称“抽流”或“解复用”，即从容器或传输流中分离出所选轨道。

示例：

- M2TS → HEVC + TrueHD + PGS；
- MKV → FLAC + ASS；
- MPLS 所定义的蓝光播放内容 → 来自多个具有时间边界的 M2TS 片段的所选流。

抽流本身不必解码或重新编码。正确的复制式抽流通常会保留编码访问单元，但由于源和目标的封装表示不同，外围帧结构、时间戳、延迟表示或编解码私有头仍可能改变。

对 MPLS 抽流不等于简单拼接文件。每个播放项都选择一个片段及其 `INTime`/`OUTTime` 窗口。同一 M2TS 可以以不同时间窗口重复使用，不同播放项也可能具有不同的轨道布局。

## Mux 与 Remux

**Multiplexing** 通常简称 **mux**，中文常称“混流”或“复用”，即把轨道和元数据组合进容器。

**Remuxing** 通常简称 **remux**，中文常称“重混流”，即从现有容器或原盘结构读取轨道，在不重新编码被复制流的情况下将其写入新容器。

纯重混流会：

1. 读取编码数据包；
2. 按需要调整容器时间戳和元数据；
3. 将这些数据包写入新容器。

解码后的画面或声音没有重新生成，因此被复制的流不会产生新的编解码世代损失。但输出文件并不会与输入逐字节相同：容器头、交织方式、时间戳、轨道顺序、名称、语言标签、章节和附件都可能发生变化。

在 BluraySubtitle 中，“Blu-ray Remux”是一个产品工作流名称。视频不会重新编码，但该工作流可能：

- 保留或排除所选轨道；
- 按 MPLS 播放项窗口和所选章节裁切；
- 连接多个片段；
- 应用轨道语言和章节；
- 在启用选项时将所选无损音频转换为 FLAC；
- 按已记录规则移除静音或完全重复的音轨；
- 将兼容的 Dolby Vision 输入转换为项目支持的 profile 8.1 结果。

因此，不能把“Remux”理解成“复制原盘中的每一个字节”。

## Decode、Encode 与 Transcode

**解码（decode）**将压缩或编码轨道转换成可使用的样本：

- H.264/HEVC → 视频帧；
- FLAC/TrueHD/AAC → PCM 音频；
- PGS → 字幕位图及合成指令。

**编码（encode）**将样本转换成编码流。视频编码通常包括预测、变换、量化、熵编码和码率控制；音频编码可以是无损或有损的。

**转码（transcode）**是“解码一种表示，再编码为另一种表示”的完整过程。转码还可能包括缩放、降噪、去色带、色彩转换或字幕渲染等预处理。

BluraySubtitle 的 Encode 工作流通常包含以下概念阶段：

1. 将所选蓝光内容重混流为稳定的暂存源；
2. 通过处理管线解码视频；
3. 可选地用 VapourSynth 处理视频帧；
4. 使用 x264、x265 或 SVT-AV1 编码；
5. 按每条音轨的策略处理所选音频；
6. 将字幕输出为外挂、软字幕或硬字幕；
7. 混流并验证最终结果。

**软字幕（softsub）**仍是播放时可选择的字幕轨。**硬字幕（hardsub）**会在编码前渲染进视频帧，播放时无法关闭。

## 无损与有损

**无损（lossless）**和**有损（lossy）**描述的是一次编码能否精确重建其输入样本。

### 无损

无损编解码器能够逐位重建原始解码样本。示例包括：

- 用于 PCM 音频的 FLAC；
- 无损的 TrueHD/MLP 音频；
- DTS-HD Master Audio 的无损扩展；
- 某些编码器提供的无损视频模式。

无损不代表未压缩。FLAC 会压缩数据，但能够精确重建输入 PCM。

### 有损

有损编解码器会有意丢弃信息以降低码率。示例包括：

- 蓝光常规用法中的 AVC/H.264 和 HEVC/H.265；
- 常规 MPEG-2 Video 和 VC-1；
- AC-3、E-AC-3、AAC、DTS core 和 Opus。

损失在视觉或听觉上可能很小，但解码输出不再与编码器输入完全相同。

### 重要限定

- **无损容器操作不是编解码器。** 重混流可以原样保留编码轨道，即使轨道本身最初使用的是有损编码。
- **无损转无损保留的是解码样本，不一定保留所有附属元数据。** TrueHD 转 FLAC 可以保留所选解码结果的 PCM，但无法在 FLAC 中继续保留 Atmos 对象元数据。
- **无损源不会让有损编码变成无损。** LPCM → AAC 仍然是有损转换。
- **反复进行有损编码会产生世代损失。** AVC → 原始帧 → HEVC 即使使用高码率，也会引入新一代损失。
- **位深不等于无损。** 标称 24-bit 的容器可能只有 16 位有效精度；降低位深也可能有损，除非被丢弃的位本来就没有信息。

## 原盘、BDMV 与 BDRip

在本项目中，**原盘源**一般指保留蓝光应用结构的可读取备份、已挂载镜像或目录。关键目录是 `BDMV`，其同级目录通常还有 `CERTIFICATE`。

**BDMV** 不是单个媒体文件，而是蓝光应用与媒体目录树。它告诉播放器：

- 有哪些标题；
- 应启动哪个导航对象；
- 哪些播放列表定义播放内容；
- 每个播放列表由哪些 M2TS 片段和时间窗口组成；
- 每个播放项包含哪些流；
- 章节和入口标记位于何处。

**BDRip** 是社区术语，并不对应唯一精确的格式。它通常指从蓝光制作出的发布成品，往往包含画面处理和重新编码。**BDRemux** 一般指保留源视频流，并将所选原盘内容重混流到 MKV 等消费级容器中的成品。

## 实际示例

假设某个 MPLS 定义如下：

| 播放项 | M2TS 片段 | 窗口 | 内容 |
| ---: | --- | --- | --- |
| 0 | `00010.m2ts` | 00:00–00:12 | 制作商片头 |
| 1 | `00020.m2ts` | 00:05–24:10 | 正片 |
| 2 | `00030.m2ts` | 00:00–00:08 | 版权提示 |

该播放列表不等同于任何一个 M2TS；它是由三个时间窗口构成的虚拟时间线。主内容选择可以只保留正片窗口。按照项目规则，未选中的制作商片头和版权提示随后可以归入 SP。

如果所选视频轨是 AVC，并且原样复制进 MKV，这属于视频重混流。如果将它解码、滤镜处理并编码为 HEVC，则属于视频转码。如果 LPCM 音频编码为 FLAC，该音频转换是无损的；如果编码为 AAC，则是有损的。

## 常见误区

### “最大的 M2TS 就是电影”

经常如此，但并不可靠。无缝分支、重复使用的片段、多角度内容、剧集连播和播放列表混淆都会使文件体积产生误导。真正的编排播放路径由 MPLS 播放项及其时间窗口表达。

### “最长的 MPLS 一定是主 MPLS”

不是。诱饵播放列表可能更长，同一张原盘也可能存在多个合法的主播放列表。由于仅凭时长无法始终推断内容语义，BluraySubtitle 允许手动选择。

### “MKV 表示视频已经压制过”

不是。MKV 是容器，内部视频既可能是原盘直接复制，也可能是重新编码的结果。

### “Remux 表示保留所有轨道”

不是。重混流通常仍会选择轨道。BluraySubtitle 还会执行已记录的音频转换和清理策略。

### “无损音频一定更小”

不是。FLAC 可以有效压缩 PCM，但已经压缩过的无损格式可能比其解码后重新编码得到的 FLAC 更小。文件大小和是否无损回答的是两个不同问题。

### “提取出的裸流会保留完整源时间线”

不一定。容器时间戳、编辑信息、延迟和空隙可能无法在裸基本流中等价表示。
