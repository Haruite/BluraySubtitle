## 用途

本文档长期记录 Python 重构情况，包括每个已完成阶段或工作流修改了什么、业务逻辑如何变化、执行了哪些测试，以及哪些内容被明确推迟。

Phase 1 的详细分析仍保存在 [第一阶段重构契约与配置矩阵](phase-1-contract-and-configuration-matrix.md) 中。后续所有修改还必须遵守强制性的[代码修改规范](../development/code-standards.zh-Hans.md)。

## 维护规则

每次完成重构或重大改动，都必须在同一次修改中同步更新本文档及其英文版本；一般修改不需要增加历史记录。每条记录必须包含：

- 范围与提交；
- 删除的冗余或冲突路径；
- 业务逻辑变化，包括旧行为和新行为；
- 文档与 i18n 变化；
- 自动检查及仍需使用真实素材完成的手动检查；
- 明确推迟的工作。

历史记录必须遵循作者已经记录的意图；尚未确定的行为应标记为待确认，不能为了补全文档而自行给出结论。

## Phase 3.2——添加章节工作流

日期：2026-07-20 提交：`107cea1`（`refactor: unify add chapters workflow`）

### 范围

将“添加章节”重构为独立的 GUI Request、后台 Worker 和纯数据 Service 路径。

### 删除的冗余或冲突路径

- 删除 GUI 线程中的同步执行。
- 删除吞掉 GUI 配置错误后回退到旧表格/配置逻辑的路径。
- 删除 Service 边界中的 Qt 表格对象。
- 删除对工作目录共享 `chapter.txt` 的依赖。
- 删除对 `completion()` 的调用，避免把“直接编辑原文件”误解为允许补全蓝光目录。

### 逻辑变化

- 请求在启动时一次性捕获当前可见 MKV 顺序、所选主播放列表、准确的源/输出路径对和直接编辑模式。
- MKV 与所选播放列表根据时长和章节点按顺序匹配，不要求文件名包含 `BD_Vol_NNN`。
- 修改任何 MKV 前先完成全部章节文档规划；所选播放列表无法覆盖全部 MKV 时，在写入前失败。
- 主播放列表、MKV 输入、所需 MKVToolNix 程序、重复路径和已有输出在可预知时于 Worker 启动前检查。
- 已存在输出明确报错。
- 每个任务使用独立临时章节文件。
- `mkvmerge`、`mkvpropedit` 不再通过 shell 命令字符串执行，失败返回码会被报告；MKVToolNix 返回码 1 仍视为带警告的成功。
- 只有单个零点章节时，直接编辑仍保持源文件不变；新文件模式仍会生成 MKV，但不会加入这个无意义章节。

### 文档与 i18n

- 同步更新中英文 README，记录顺序、播放列表匹配、直接编辑/新文件模式、预检查和输出冲突规则。
- 新增工作流、工具、映射和命令失败所需的中英文信息。
- 同步 Worker 导出以及 GUI/Service IDE 基类契约。

### 验证

- 新增不可变请求捕获、直接编辑、当前表格顺序、输出冲突、无卷号文件名的多播放列表顺序匹配、写入前映射失败、Worker/Service 边界及单章节输出测试。
- 集中执行仓库测试，共 49 项全部通过。
- Python 编译、i18n 审计、split 契约审计、`git diff --check` 和 CRLF 检查通过。

### 仍需真实素材验证

## Phase 3.3——原盘 Remux 工作流

日期：2026-07-22 提交：`b89f995`（`refactor(remux): rebuild main playlist workflow`）

### 范围

重构 Remux 的 GUI 请求、Worker 边界、预执行规划、主播放列表执行和最终输出映射。保留已有 fallback 算法，但每个已选择主播放列表现在都在一个确定的独立任务中执行。

### 删除的冗余或冲突路径

- 删除 Worker 中镜像 GUI 状态的大量参数和重复的 Service 配置赋值。
- 删除按原盘分组后执行的路径；旧路径在同一原盘存在多个已选择主播放列表时可能只执行第一个。
- 删除提前创建输出目录、随后再扫描目录以重新发现本任务输出的逻辑。
- 删除输出名称字符自动替换、数字冲突后缀和回退到无关原始输出文件的逻辑。
- 删除强制启用“补全蓝光目录”的逻辑。

### 逻辑变化

- 一个自有 Remux 请求一次性捕获当前 GUI 配置、已选择主播放列表、可见输出名称和语言、SP 行、轨道设置、默认音频编码、电影模式、裁剪、Dolby Vision 和目录补全选项。
- 按界面可见顺序规划主播放列表。每个已选择主播放列表必须生成且只生成一条非空命令和一个执行任务，同一原盘中的多个主播放列表也不例外。
- GUI 命令预览与执行逻辑现在共同使用同一个七项命令结果。命令生成失败时预览保持为空，并在捕获配置时被拒绝，不再合成一条缺少计划输出路径和轨道参数、但看起来可以执行的命令。
- 创建输出目录前推导所有命令理论输出和最终 GUI 输出路径，并在写入前校验配置行数、章节范围、重复路径和已存在文件。
- 最终名称严格按照界面显示值应用；没有 `.mkv` 扩展名时补充扩展名，无效的 Windows 文件名明确报错。
- 主命令或 fallback 必须生成对应任务规划的全部输出。缺少输出时任务现在会失败，不再静默跳过；失败后删除本任务新建的预期中间输出。
- 收尾处理直接使用规划输出列表，不再扫描目标目录，并使用任务独立的临时章节文件。
- 无论是否勾选目录补全，章节元数据都会直接写入本任务新生成的输出；该复选框现在只控制蓝光目录补全。
- 每个主播放列表任务都会捕获“编辑轨道”保存的语言，并在创建输出前检查 `mkvpropedit` 是否可用。主命令或任一 fallback 成功后，只对实际包含轨道应用已配置语言，修改后重新识别输出并验证；映射、命令或验证失败都会使任务失败并删除该任务新建的主输出。
- 剧集输出顺序继续与配置顺序对齐，供后续字幕、语言、SP、音频和 Dolby Vision 处理使用。
- “补全蓝光目录”严格使用捕获到的复选框值。

### 文档与 i18n

- 同步更新中英文 README，记录一个主播放列表对应一个任务、写入前输出规划、精确命名、冲突处理、严格完整性、复选框所有权和经过验证的主输出语言修正。

## Phase 3.4——原盘 Encode 主流程

日期：2026-07-22 提交：`d4adee2`（`refactor(encode): unify Blu-ray and Remux encode workflows`）

### 范围

重构 Encode 的启动、Worker、原盘暂存及原盘/Remux 两种输入共用的逐行执行路径。SP 混流算法、轨道对齐、缺轨修复、音频转换算法和 Dolby Vision 算法仍留在后续对应工作流中。

### 删除的冗余或冲突路径

- 删除 GUI 中原盘/Remux 两套重复的启动分支、线程清理和信号连接。
- 删除 Worker 镜像 GUI 状态的大量参数，改为一个不可变 Encode 请求。
- 删除 `EncodeMkvFolderWorker` 以及 Service 内同步嵌套调用 Worker 的路径。执行错误现在会直接传递给唯一的 GUI Worker，不再由内部 Worker 转成信号后被外层继续当作成功。
- 删除字幕、输出名称、语言、VPy 路径、配置和 SP 条目的并行数组；每个可见行直接拥有相关值和准确输出路径。
- 删除 Remux 后扫描目录以重新发现暂存正片输出的逻辑。
- 删除 Encode 对隐藏“补全蓝光目录”复选框的读取、强制启用状态以及 `completion()` 调用。
- 删除旧有的已有输出静默跳过、复制失败尽力忽略及运行时重新生成缺失显式 VPy 文件的行为；Remux 来源恢复执行改为遵循一条明确记录的统一规则。

### 逻辑变化

### M2TS 与媒体映射

- 扫描结果就绪、worker 身份、线程清理、待启动任务和扫描失败现已分别记录。worker 已计算的轨道选择会直接应用，不再在 GUI 线程重复探测同一 MPLS。在当前扫描期间点击 Remux 或原盘 Encode 会进入等待，并且所有结果完成应用后扫描线程才可退出；只有扫描及输出名重算成功后，才会将同一功能自动启动一次，失败或取消不会启动任务。
- 被替换 worker 的结果、完成和失败信号都会忽略。扫描失败在线程退出后仍保持无效，因此再次点击 Remux 不能绕过失败；刷新来源会启动新扫描，且只有新扫描有效时才清除失败状态。

## 第六阶段后——恢复确定性的音轨清理

日期：2026-07-25 提交：包含在本次修改中

### 范围

### 逻辑变化

- 最终原盘 Remux 和 Encode 混流会分析每条已选择的音轨。即使关闭无损转 FLAC，Remux 仍执行清理；原盘 Encode 暂存阶段仍完全保留音频，只在视频压制成功后执行最终清理。
- 一条 `mkvextract` 命令会把全部已选音轨从源 Matroska 提取到当前任务的暂存目录；分析与转换复用这些文件，不再针对每条音轨重新读取巨大的源容器。
- 每条提取出的音轨由 FFmpeg 完整解码一次，同时取得 `volumedetect` 最大音量和确定性的 8 kHz PCM SHA-256 指纹。最大音量低于 -60 dB 时移除静音轨。提取或分析失败会明确报错，并在来源边界允许时提前检查所需 MKVToolNix 和 FFmpeg。
- 只有源编码家族、声道数和解码指纹均相同的音轨才参与重复判断。已知语言不同的音轨保持独立；确认重复时移除后出现的轨道并保留源顺序中最早的一条。后续转换和最终 `mkvmerge --track-order` 都使用同一个明确的保留轨道列表。
- 实现只使用已捕获的 Matroska 轨道 ID，不扫描输出目录，不根据 `.track` 文件名猜测归属，也不会读取无关残留文件。
- DTS 系列转换出的 FLAC 只有在不大于提取出的 DTS 时才替换源轨道。更大的 FLAC 会删除，并在原位置保留 DTS；PCM 和 TrueHD/MLP 成功转换出的 FLAC 不受体积限制。

- 每行探测最终 VPy 实际读取的媒体：直接 Remux MKV、任务自有的原盘暂存 MKV，或为 x265 准备的 Dolby Vision 基础层 HEVC。探测位于来源准备之后，不会误读蓝光根目录、MPLS 或已被替换的容器。
- 一次 FFprobe 同时读取第一条视频流和首帧；由于 HDR 静态 SEI 可能只存在于帧级记录，首帧 side data 会去重后合并。缺少 HDR 字段不使来源无效，探测只记录可用视频流与编码格式，不提前分类。
- 来源探测或元数据规划失败属于非阻塞错误：使用用户参数继续压制，新建带数字后缀且不覆盖旧文件的 `<输出名称>.hdr-metadata-error.txt`，并在 Worker 清理后统一报告警告。
- 一套解析器为全部编码器和输入类型规范化色彩范围、原色、传递特性、矩阵、色度位置、母版显示及 MaxCLL/MaxFALL。x264 使用其色彩参数及 `--mastering-display`、`--cll`；x265 使用 `--master-display`、`--max-cll`；SVT-AV1 使用 H.273 值及转换后的母版坐标和物理亮度。
- 界面手动参数始终优先。同名手动参数只抑制对应自动项；x264 `--fullrange` 也抑制范围，x265 `--video-signal-type-preset` 抑制全部自动色彩／HDR 静态参数。程序不推导 `--hdr10` 或 `--hdr10-opt`，并跳过格式异常或不支持的单项值。
- 最终 VPy 准备后抽查输出 0 的首帧、中间帧和末帧。稳定的 VapourSynth 范围、原色、传递、矩阵及色度属性覆盖来源值，缺失属性回退到 FFprobe；抽查不一致只使当前行失败。
- VPy 改变原色或传递特性时会丢弃来源母版显示／CLL，并停止保留 Dolby Vision，避免把过期元数据附到已改变的画面。其他 VPy 探测失败通过警告路径继续使用来源快照。

### HDR10+、Dolby Vision 与 x265 能力兼容

- ST 2094-40 会为 x265 10/12 位输出启用 HDR10+ 自动流程。`hdr10plus_tool` 提取经校验的 JSON，其帧数和来源帧率必须与 VPy 时间轴一致；手动 `--dhdr10-info` 仍然优先。
- 程序探测实际配置或随程序提供的 x265 是否声明 `--dhdr10-info`、`--dolby-vision-profile` 和 `--dolby-vision-rpu`。结果按规范化路径、大小和修改时间缓存，自编译二进制被替换后无需依赖版本字符串即可失效。
- “外部工具”设置检查复用该探测：只有 x265 声明 `--dhdr10-info` 时才要求 `hdr10plus_tool`，只有两项 Dolby Vision 输入参数同时存在时才要求 `dovi_tool`；缺少对应能力的构建不会产生辅助工具缺失警告。
- 只有实际声明能力时才传入原生参数。缺少或未验证的原生 HDR10+ 使用经过验证且原子替换的 `hdr10plus_tool` 后注入；Dolby Vision 使用受检查的 `dovi_tool` 注入。HDR10+ 注入后再次检查仍启用的 RPU，失败时不替换原编码码流。
- 原生 Dolby Vision 要求 x265 10/12 位输出，并且当前行已经具备两个 VBV 参数和母版显示信息。程序不会擅自生成 VBV；缺少前提时在压制后注入已提取的 Profile 8.1 RPU。
- 只有两条原生路径及全部 Dolby Vision 前提都存在时，HDR10+ 与 Dolby Vision 才共用一次 x265 压制。最后一次注入后、混流前检查两种元数据。要求保留 Dolby Vision 时拒绝 x264 和 x265 8 位；SVT-AV1 因当前工具链不能制作 AV1 Profile 10，会继续压制但省略 Dolby Vision。
- 受管理 x265 的全部链接核心都启用 `ENABLE_HDR10_PLUS` 并声明两项 Dolby Vision 输入；构建标记会替换缺少能力的旧同版本受管理构建，运行时探测则继续兼容用户自行编译的二进制。
- 提取、时间轴或验证失败时保留普通 HDR 静态压制，并按逐行规则保留有诊断价值的非空 JSON／RPU；只有最终混流成功后才删除已经验证的临时元数据。

## 自动 getnative 分析与缩放核一致性

日期：2026-08-02 提交：a5fa237

### 执行与检测修正

- 保留应用本机 Python 与便携版 Python 3.13 VapourSynth 所需的分离运行结构：本机侧模块负责曲线和多帧排名，`getnative.vpy` 在 `vspipe` 中负责图片加载、逆缩放／重缩放评估及指标收集。
- RGB 样本 PNG 现在先按上游做法用 BT.709 从 RGB 转亮度，再转成 32 位浮点 `GRAYS`。旧路径会在 L-SMASH 将 FFmpeg PNG 加载为 `RGB24` 时直接选择 RGB 第 0 平面，实际测量的是红色通道而非画面亮度。
- 优先扫描仍会报告全部 16 种配置核。前三种优先核一定执行细扫；后续核只有在同尺度半尺寸粗扫得分明显更弱时才跳过细扫。无效或不完整曲线不能成为获胜核，也不能影响全局最佳值。
- 核共识要求配置数量的完整有效曲线落在真实的 2 像素窗口内，而且不能早于 `min_kernels` 停止。自动 Encode 调用方会尝试全部 16 种核，并流式输出被明确跳过的粗筛结果。
- 获胜核复核仍会输出严格单调下降比例诊断，但自动排名使用既有的宽松曲线有效标记，避免丢弃本来就稀少的可用样本。多帧聚合按四舍五入高度分组，并用每组最高三个 `min(得分, 2) × 归一化高度⁴` 权重排名。得分饱和可防止低噪声伪缺口压过本来强势的组，同时在可用样本稀少时仍允许高分辨率单样本胜出。
- 曲线选择重新把 Infiziert90/getnative 的相邻高度误差突降作为主要缺口信号，并返回可直接跨帧比较的 `前一高度误差 / 当前高度误差` 比值作为得分。原有平滑谷底仅在没有可信尖锐缺口时回退；540p、1040p 后、局部振荡和不稳定尾段排除会在两类结果胜出前生效。
- 已确认的 535p 至 545p 排除规则继续覆盖主选择、回退选择和分段细化选择，并新增无条件排除高于 1040p 的候选；原有的振荡尾段抑制在该边界以下继续生效。确实为原生 540p 的素材仍需手动设置 VPy。

### 运行时应用、性能与所有权

- 新生成的 Encode VPy 现在会准确应用检测核：8 组 Bicubic 参数、Lanczos taps 2～5、Bilinear，以及 Spline16／36／64。旧模板会把所有 Lanczos 固定为 taps 3、所有 Bicubic 固定为 b/c 1/3，并让 Spline 结果进入 Bicubic 分支。

## PlayItem 逻辑轨道与稀疏 Matroska Remux

日期：2026-09-03

### 选轨与兼容性契约

- 用汇总全部 PlayItem 的逻辑轨道替代只读取首个 PlayItem STN 的模型。同一 STN 类别和 Stream Number 序号表示一条逻辑轨道；各片段可以使用不同 PID，没有片段表示时间线空档，不是需要合成的缺失流。
- 原盘加载期间，“编辑轨道”继续只读取 MPLS，并按第一次出现的 PID 排列。界面现在显示逻辑轨道名、全部不同 PID 和简明状态，提示中列出逐 PlayItem 的 PID／语言时间线。默认语言取第一次出现的非 `und` 明确语言，后续语言变化会显示，但不改变轨道身份或默认值；MPLS 编码或呈现参数发生无法由一条稳定 Matroska 轨道表达的变化时，整行会被禁用。
- 实际执行时，内部 M2TS 解析器把每个已声明片段与对应 PlayItem M2TS 的 PAT/PMT 逐一核对。默认情况下，已声明 PID 缺失或传输流类型冲突时，因为 GUI 已选逻辑轨道无法保留，该输出会终止；任务不会静默缩减选择后继续。STN 空档仍作为稀疏区间保留，不触发替代轨生成。

### 直接混流与回退变化

- MKVToolNix 分析继续推迟到执行阶段。只有 MPLS 和每个 PlayItem M2TS 都能为保留的逻辑轨道片段提供一致的本地轨道 ID 映射时，才使用直接 MPLS 混流；PID 变化在映射保持一致时允许，空档或 MKVToolNix 漏轨则进入回退。
- 回退改为按 PlayItem 片段工作，不再使用一套参考 PID 布局。每个分段只包含当前 PlayItem 已声明的已选片段；先尝试 MKVToolNix，只有 MKVToolNix 遗漏已声明 PID 时才用 tsMuxer 恢复，不生成静音或空轨。
- 用一次最终 `mkvmerge` 写入替代反复的文件级拼接。逻辑轨道第一次出现的片段以绝对播放列表偏移作为普通输入，后续片段通过链式 `--append-to` 和逐轨空档偏移连接；既保留开头／中间空档，也不为每条逻辑轨道反复重写不断增长的成品。
- 轨道对齐回退本身只复制码流，内部不执行音频转换；完整 Matroska 产物仍进入共用的 Remux 后音频阶段，因此直接 Remux 和回退 Remux 之后的转换选择保持一致。带稀疏播放列表时间线的独立音频输出会明确失败，因为裸音频流无法在不插入样本的情况下保存空档。

### 稀疏音频后处理

- 将回退逻辑音轨的全部区间传递到共用的最终 Remux／Encode 音频路径。FLAC、AAC 和 Opus 现在只处理实际连续 PCM 区间，并在不合成静音的情况下重建开头或中间 Matroska 空档；静音与重复分析同样把区间布局纳入判断。
- 正常批量提取继续只读取一次源媒体。批量失败时以包含全部区间的逻辑轨道为单位重试；任一区间提取、有效位深检测、编码、时间线重建或验证失败，都会把完整逻辑轨道回退为原始码流。
- 时长验证由整轨比较改为排除编排空档的区间窗口。提示与回退采用单个区间最大的正向缩短量，不累加各区间损失，使阈值对应可能产生的最大听感延迟。
- 稀疏 AAC／Opus 分别编码各区间，先规范为单轨 Matroska 输入，再通过一次追加操作重建逻辑轨道。MKVToolNix 会拒绝追加分别编码的 FLAC 码流，因此稀疏 FLAC 使用一个 FFmpeg 编码流及明确时间戳间断；真正 32-bit 的稀疏 FLAC 保持原轨，不通过 FFmpeg 的 24-bit 限制降位深。

### 可选的非视频片段物理缺失处理

- 在“高级”中增加默认关闭的“允许非视频轨道部分缺失”，并把该值捕获到 Remux 与 Encode 请求。以 BDMV 为来源的 Encode 会把它传给暂存 Remux；Remux 来源 Encode 不需要播放列表恢复。
- 选项关闭时继续严格报错。启用后，只有内部 PAT/PMT 解析确认不存在的已选音频或字幕片段可以继续进入回退。程序仍先探测 tsMuxer；如果它也无法提供该 PID，才从当前 PlayItem 的预期布局中移除，并记录为时间线空档。视频缺失、格式冲突、解析结果不确定，以及 tsMuxer 分离或合并失败仍属于致命错误。
- 最终回退拼接要求每条已选逻辑轨道在输出窗口中至少实际出现一次。由此生成的音频区间信息只包含真实连续区间，并传给原有的 Remux 后 FLAC／AAC／Opus 与清理流程；回退本身不处理音频转换。

### 删除路径与明确边界

- 删除按命令区间选择 PlayItem 的辅助函数，以及过时的首个 M2TS／参考布局回退假设。无 MPLS 的单 M2TS SP 仍保留源文件本地轨道 ID 路径，因为它不属于 MPLS 逻辑轨道工作流。
- 兼容性检查限制在 MPLS 和 PAT/PMT 可以公开的元数据内。PCM 参数或 codec-private 数据等仅载荷可见变化无法由这些元数据确认，因此有意不预先解析或归一化。如果 MKVToolNix 拒绝此类追加，回退会失败，任何局部分段都不会提升为成品。

## Remux 空档传递与跨 MPLS 物理轨道身份

日期：2026-09-03

### 音频时间线传递

- Remux 完成音轨间隙检测后会在最终 Matroska 成品旁生成一个 `.audio-gaps.json`。文件记录空档而不是 PCM 区间，并与准确的成品大小及相关轨道 UID 绑定；连续输出保留有效的空记录文件，使后续 Encode 能区分“确认连续”和“仍需检测”。
- Remux 来源 Encode 会在音频处理前验证并读取该文件。文件缺失或无效时，现有的 FFmpeg 多输出 Wave64 提取使用具名 `ashowinfo` 滤镜记录数据包时间戳。检测到的间断会从已经解码的 Wave64 中生成区间，因此回退发现过程不会再次读取来源 MKV。
- 回退区间缓存现在会随每个主输出重命名移动到最终文件名，供 Remux 后清理／转换使用，并且只在最终原子混流完成后写出。任务失败清理输出时也会删除该输出拥有的伴随文件。

### 播放列表来源聚合

- 用绝对 `(M2TS 路径, PID)` 对应关系组成的物理轨道签名替代跨文件 PID 和 STN 槽位比较。持久化 MPLS 选择改用包含来源 MPLS／类别／槽位的键，因此不同播放列表中相同的 PID 或槽位本身不再产生冲突。
- 与整条主 MPLS 匹配的来源只能提供物理关系不与主来源或更早来源重叠的轨道。合并后的“编辑轨道”行会显示来源 MPLS 和槽位，按代表 PID 排列，并统一执行一次共用默认选轨算法。
- 完整匹配 MPLS 暴露的已选轨道不再仅因其 GUI 行属于备用来源而强制进入轨道对齐回退。主 MPLS 输入能够识别对应 PID，并且引用的各 M2TS 片段映射一致时，会使用正常的一次混流；只有主输入无法表达的布局才进入回退。
- 与单集匹配的 SP 会分别对主 MPLS 和 SP MPLS 执行共用默认选轨算法。实际附加时再次按物理签名去重，保持原剧集轨道顺序，再按选择顺序附加接受的 SP 轨道。删除了从单个传输 PID 重建 SP 身份的旧辅助函数。
- IGS 继续作为 MPLS 元数据显示，但在“编辑轨道”中禁用，因为 Matroska 没有交互图形字幕轨道表示；普通字幕回退不会再把菜单编排状态误当作 PGS。
